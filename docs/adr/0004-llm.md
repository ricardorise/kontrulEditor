# ADR 0004 — LLM opcional na análise, no assistente e na associação de mídias

Status: aceito. Padrão: **desativado** (`KONTRUL_LLM_PROVIDER=none`): nada sai da máquina e tudo funciona só com regras.

## Provedores (adaptadores HTTP em `app/llm/client.py`, sem SDKs)
| Provedor | Variáveis | Saída estruturada |
|---|---|---|
| `anthropic` | `KONTRUL_ANTHROPIC_API_KEY`; modelo padrão `claude-sonnet-5-5` | *tool use* forçado (JSON conforme o schema) |
| `openai` | `KONTRUL_OPENAI_API_KEY`; padrão `gpt-4o-mini` | `response_format: json_schema` estrito |
| `openrouter` | `KONTRUL_OPENROUTER_API_KEY` + `KONTRUL_LLM_MODEL` (ex.: `anthropic/claude-sonnet-4.5`) | idem, com degradação para `json_object`/texto se o modelo não suportar |
| `ollama` | `KONTRUL_OLLAMA_HOST` (padrão `localhost:11434`; no Docker `host.docker.internal`) + `KONTRUL_LLM_MODEL` (ex.: `llama3.1:8b`) | `format` = JSON schema |

Comuns: `KONTRUL_LLM_MODEL`, `KONTRUL_LLM_BASE_URL` (proxy/endpoint compatível), `KONTRUL_LLM_MAX_WINDOWS` (teto de chamadas por análise = controle de custo), `KONTRUL_LLM_WINDOW_WORDS`, `KONTRUL_LLM_TIMEOUT_S`, `KONTRUL_LLM_MAX_TOKENS`. Novas tentativas com *backoff* em 429/5xx; parâmetros que o modelo recusa (`temperature`, `max_tokens`…) são removidos sozinhos. Chaves nunca aparecem em logs, erros nem em `/v1/llm/status`.

## O que o LLM faz
1. **Análise** (`llm_analysis.py`): as regras geram candidatos; a transcrição é enviada em janelas com contexto. O LLM confirma/rejeita/ajusta cada candidato e aponta achados novos (tentativa descartada sem «erro», bastidor × improviso do tema, melhor tomada).
2. **Assistente** (`llm_assistant.py`): só para passos que as regras não entendem. O modelo devolve *intenções* tipadas (inserir mídia, remover trecho/frase, aceitar sugestões); o código resolve frases→tempos e monta as operações, que passam pelo mesmo dry-run.
3. **Mídias** (`llm_placement.py`): associação semântica (sinônimos/assunto) que complementa o casamento por tags.

## Salvaguardas (falso positivo é a métrica prioritária)
- O modelo só devolve **índices de palavras** que numeramos; tempos vêm da transcrição. Cada indicação exige `quote` que bata com as palavras, ficar na janela principal (nunca no contexto) e ter 0,5–120 s; senão é descartada e contada (`dropped_invalid`).
- Achados só do LLM nascem com confiança **no máximo "média"**. Discordância do LLM com uma regra **não apaga** a sugestão: ela fica marcada ("LLM discorda") com confiança baixa. Tudo continua `pending` até o usuário decidir.
- Transcrição, roteiro e pedido vão como **dado** entre tags (com `</` neutralizado); o modelo só responde JSON de schema fixo; nada é executado. Regras de proteção do usuário também valem para achados do LLM.
- Falha/indisponibilidade/timeout do LLM **nunca derruba** a análise: segue só com regras e registra o motivo em `job.result.llm`. Há heartbeat durante as chamadas.
- `use_llm`: omitido = usa se configurado; `false` = só regras; `true` = exige (409 se indisponível). A UI mostra provedor/modelo, se o texto sai da máquina, o resumo da última análise e o raciocínio do modelo em cada ocorrência.

## Limites conhecidos
- **Não validado contra as APIs reais** (sem chave no ambiente de desenvolvimento): os adaptadores foram testados contra servidores HTTP simulados no formato documentado de cada API, e o fluxo completo contra `scripts/fake_llm_server.py` (que NÃO mede qualidade). Antes de confiar, rode uma análise real e confira as sugestões.
- Nomes de modelo padrão (`gpt-4o-mini`) e slugs do OpenRouter podem mudar; ajuste `KONTRUL_LLM_MODEL`.
- A associação de mídias e o assistente com LLM rodam dentro da requisição HTTP (podem levar segundos a minutos em episódios longos).
- Custo: ~1 chamada por 700 palavras de fala (teto `KONTRUL_LLM_MAX_WINDOWS`). Tokens usados aparecem em `job.result.llm`.
